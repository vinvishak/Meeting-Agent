# Implementation Plan: Real-Time GitHub Activity Stream

**Branch**: `009-github-live-stream` | **Date**: 2026-05-03 | **Spec**: [spec.md](spec.md)  
**Input**: Feature specification from `/specs/009-github-live-stream/spec.md`

## Summary

Receive GitHub push webhooks the moment a commit lands, persist each commit and its Jira ticket references to SQLite, and broadcast a live event to all connected dashboard clients via Server-Sent Events — so engineers see new commits appear within 5 seconds, without a page refresh.

The implementation uses Python + FastAPI (existing stack), an in-process asyncio queue broadcaster (no external message broker), and vanilla JS `EventSource` in the frontend. All four components are already implemented; this plan documents design decisions and serves as the authority for the task list.

## Technical Context

**Language/Version**: Python 3.12+ (backend) · HTML5/CSS3/JavaScript ES2022 (frontend)  
**Primary Dependencies**: FastAPI + Starlette (existing) · APScheduler (existing) · SQLAlchemy 2.x async (existing) · Alembic (existing) · `hmac`/`hashlib` stdlib · `asyncio` stdlib  
**Storage**: SQLite via Alembic migrations — 4 new tables added in `002_github_schema.py` (github_repos, github_commits, github_pull_requests, github_jira_links)  
**Testing**: pytest + pytest-asyncio (existing)  
**Target Platform**: Single-process uvicorn on Linux (Railway); browser clients via HTTPS  
**Project Type**: Web service (FastAPI) + single-file frontend dashboard  
**Performance Goals**: Commit appears on dashboard within 5 seconds of webhook receipt; webhook endpoint responds in < 200 ms (ingestion offloaded to background task)  
**Constraints**: Single-process only (in-process broadcaster; no horizontal scaling for MVP) · EventSource API does not support custom request headers (stream endpoint must be public)  
**Scale/Scope**: Single engineering org; low webhook volume (< 100 pushes/day typical)

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Principle | Status | Notes |
|-----------|--------|-------|
| I. Modular & Clean Code | PASS | `broadcaster.py` owns only fan-out logic. `webhooks.py` owns only HTTP ingestion and SSE serving. No cross-module side-effects. |
| II. Single Responsibility | PASS | Each module has one job. HMAC validation is a pure function (`_verify_signature`). Ingestion is isolated in `_ingest_push`. |
| III. Test-First | **WARN** | Implementation was built before tests. Tests must be added as the highest-priority tasks to restore compliance. No new logic may be shipped untested after this plan. |
| IV. Agent Composability | PASS | `broadcast()` accepts any JSON-serializable dict and has no knowledge of callers. `subscribe()`/`unsubscribe()` are stateless from the caller's perspective. |
| V. Simplicity First (YAGNI) | PASS | In-process queue chosen over Redis; SSE chosen over WebSocket. Both are the simplest solution that meets the spec. |
